# 프로젝트 공통 약관·개인정보·관리자·감사로그 개발 표준

표준 ID: PROJECT-GOVERNANCE-1.0  
작성일: 2026-09-07  
상태: 다른 프로젝트에 전달할 공통 개발 기준안  
적용 환경: 한국에서 운영하는 회원 기반 웹 서비스. 기본 서버 환경은 Windows / Cloudflare / Caddy / Waitress / Django. 다른 환경에서도 기능·기록·화면 계약은 유지하고 구현체만 조정한다.

## 0. 이 문서를 전달받은 LLM에게

이 문서는 특정 프로젝트의 기능을 무조건 복제하라는 지시가 아니다. 이용약관, 개인정보처리방침, 관리자 페이지, 감사로그를 프로젝트마다 같은 기준으로 조사·설계·구현·검증하라는 지침이다.

사용자가 작업을 요청하면 이 문서와 대상 프로젝트를 조사하고 `PROJECT-ADOPTION.md`를 먼저 채운다. 사용자 요청 범위에서 구현을 진행하며, 없는 서비스·수집정보·외부업체·법적 의무를 만들어 넣지 않는다. 기존 동작과 운영 설정을 확인하고 재사용한다. 기존 데이터를 임의 삭제하거나 운영 설정·공개 법률 문서를 검토 없이 덮어쓰지 않는다.

프로젝트가 작다는 이유로 공통 필수 항목을 생략하지 않는다. 반대로 다른 프로젝트에 있다는 이유로 결제·광고·위치정보 등 없는 기능을 도입하지 않는다. 비해당 항목은 적용표에 이유를 남긴다.

문서 분량 자체가 아니라 다음을 일치시킨다.

**실제 기능 → 처리 정보 → 법적 근거·기간 → 서버·앱 구현 → 관리자 화면 → 공개 안내 → 검증 결과**

이 문서의 법률 관련 설명은 법적 적합성이나 수사 증거력을 보증하지 않는다. 작업 시 공식 법령의 최신 조문과 시행일을 확인하고 프로젝트별 적용 여부를 구분한다. 적용 여부가 불명확하면 독립 작업은 계속하되 의존하는 수집·공개·기간 확정은 미확정으로 남긴다.

## 1. 사용자 요구에서 고정할 원칙

| ID | 공통 원칙 |
|---|---|
| CORE-01 | 동일한 데이터 처리·기능에는 동일한 설명과 보호 수준을 적용한다. 임의 요약으로 필수 항목을 누락하지 않는다. |
| CORE-02 | 기존 Caddy 접속 로그, Waitress 오류 로그를 유지한다. Django에서 전체 HTTP 접속을 중복 저장하지 않는다. |
| CORE-03 | Django는 인증 계정과 실제 행동·대상·결과를 연결하는 이벤트를 기록한다. |
| CORE-04 | 이용자 행동 로그의 원본은 별도 날짜별 JSONL 파일에 저장한다. 프로젝트 서비스 DB 저장으로 임의 변경하지 않는다. |
| CORE-05 | 관리자 조치 이력과 이용자 행동 로그를 구분하고 기존 관리자에서 각각 조회한다. |
| CORE-06 | 저장 경로·필드·행동명·권한·조회 UI·기간 계산 방식은 공통 계약을 따른다. |
| CORE-07 | 비밀번호·세션·토큰·POST 본문·게시물 원문을 행동 로그에 넣지 않는다. |
| CORE-08 | 개발 PC와 운영 서버를 구분한다. 개발 중 운영 디렉터리나 예약 작업을 임의 변경하지 않는다. |
| CORE-09 | 수사 협조는 적법한 요청의 근거·범위 확인과 필요한 기록의 보존·제공 절차로 다룬다. 자동 제공·무기한 수집으로 구현하지 않는다. |
| CORE-10 | 고급 분석·자동 제재·대량 병합·서버 명령 실행 등 기존 3차 확장 기능은 기본 도입 범위에서 제외한다. |

공통 기본값을 변경해야 하면 적용표의 편차 항목에 이유, 영향, 대체 방법, 검증을 기록한다. 기술적 세부 선택은 합리적으로 진행하되 데이터 수집 확대·기간 연장·권한 확대·보관 방식 변경을 조용히 결정하지 않는다.

## 2. 착수 조사 — 반드시 사실과 추정을 구분

다음을 읽고 근거 파일 또는 운영 증거를 적용표에 기록한다.

1. 계정 생성·로그인·탈퇴, 작성·수정·삭제, 공개 설정, 신고·제재, 문의 흐름
2. 모델·실제 DB 종류·외래키 삭제 관계·기존 관리자 권한
3. 현재 공개 약관·방침, 가입 동의 저장, 문서 버전·시행일
4. Caddy·Waitress 실제 배포 설정과 샘플 로그. 저장소 설정과 서버 설정의 차이
5. Cloudflare·호스팅·메일·외부 API·광고·분석·결제 서비스 사용 여부
6. 로그 저장 경로·생성 주체·파일 회전·삭제·백업·실행 계정
7. 관리자 목록·상세·모바일 메뉴·공통 CSS와 기존 테스트

샘플 로그의 사용자 정보는 답변이나 개발 문서에 복사하지 않는다. 키 이름·집계·마스킹된 예시로 설명한다. 샘플에 로그가 있다는 사실을 전체 기간 보관·무누락·IP 신뢰가 검증되었다는 의미로 확대하지 않는다.

### 반드시 작성할 내부 데이터 처리표

각 유형마다 `목적 / 항목 / 근거 / 생성·수집 경로 / 저장 위치 / 열람 주체 / 기간·기산점 / 파기 방법 / 외부 전달 / 공개 여부`를 채운다. 계정, 작성물, 반응, 신고, 문의, Caddy 접속 로그, 이용자 행동 로그, 관리자 조치 이력, 개인정보 접근기록은 서로 다른 행이다.

‘정당한 이익’은 문구만 붙이지 말고 필요성·최소성·이용자 권익에 미치는 영향을 검토한다. 처리방침 공개를 수집 동의나 법적 근거의 대체물로 취급하지 않는다. 없는 이메일·전화번호·광고·결제 정보를 복제하지 않는다.

Cloudflare가 앞단에서 요청을 처리한다면 ‘위탁 없음·국외 이전 없음’을 자동 복사하지 않는다. 계약·기능·처리 정보·위치를 확인하고 필요한 공개 항목을 결정한다. 프록시 서비스 이용은 Django 파일을 외부 저장하지 않는다는 사실과 별개의 문제다.

### 문서 버전 적용

기존 날짜 문서는 보존하고 새 버전 파일을 생성한다. 실제 게시·시행일에 화면 참조를 변경한다. 가입 시 저장하는 약관 버전과 실제 표시 문서를 맞추고 과거 동의 기록은 덮어쓰지 않는다. 개정 전후 비교·공지·추가 동의 필요성을 검토한다. 미확정 대괄호·가상 업체·미구현 보호조치는 공개하지 않는다.

## 5. 관리자 페이지 공통 기준

### 메뉴 순서

`대시보드 → 신고 관리 → 작성물 관리 → 회원 관리 → 작품/대상 관리 → 공지 관리 → 문의 관리 → 역할 관리 → 운영 기록 → 이용자 행동 로그`

프로젝트에 없는 메뉴는 비해당 사유를 기록하고 숨긴다. 다른 이름의 도메인 객체는 ‘작품/대상 관리’만 의미에 맞게 바꾼다. 개인페이지 링크 옆의 ‘관리자’ 진입과 사이트 복귀 경로를 제공한다. 전용 관리자 기본 경로는 `/manage/`이며 기존 경로를 유지해야 하면 매핑표를 남긴다.

### 기능·권한

- 활성 관리자 여부와 기능별 권한을 서버에서 확인한다. 메뉴 숨김만으로 보호하지 않는다.
- 기본 역할: 최고관리자 / 운영자 / 콘텐츠 편집자. 기능 없는 역할을 억지로 만들 필요는 없다.
- 신고·제재 권한, 작품 편집, 공지 초안과 게시, 회원 개인정보 조회, 역할 변경을 구분한다.
- 계정·권한 비활성화는 이미 열린 화면의 후속 요청에서도 적용한다.
- 마지막 활성 최고관리자의 무력화와 일반 운영자의 권한 상승을 방지한다.
- 운영 숨김과 작성자 공개 설정은 독립적으로 유지한다. 복구가 작성자 비공개를 공개로 바꾸지 않는다.
- 삭제 전 영향을 표시하고 처리 이력의 무조건적인 연쇄 삭제를 방지한다. 이력 보존 역시 필요한 범위·기간을 따른다.
- 제재 종료·중첩·해제, 문의 대기·완료·재개, 공지 초안·게시·종료를 명시적인 상태 전환으로 관리한다.

### 공통 화면 패턴

데스크톱은 사이드바·본문, 모바일은 접는 메뉴·본문을 사용한다. 목록은 `제목/설명 → 상태/요약 → 필터 → 결과 → 페이지 이동`, 상세는 `대상 → 관련 정보 → 가능한 조치 → 이력` 순서로 통일한다.

브랜드 색·로고는 프로젝트별로 허용하지만 메뉴명·필터 순서·테이블 열·상태 문구·권한 의미를 임의 변경하지 않는다. 상태는 색과 텍스트를 함께 표시한다. 키보드 초점, 입력 라벨, 빈 상태, 실패·미확인 상태, 검색 조건 유지, 모바일 줄바꿈을 검증한다.

## 6. 감사로그의 네 가지 구분

| 분류 | 의미 | 기본 저장 |
|---|---|---|
| 접속 로그 | 어떤 HTTP 요청·응답이 있었는가 | 기존 Caddy 파일 |
| 오류 로그 | 실행·처리 중 어떤 오류가 발생했는가 | 기존 Waitress 파일 |
| 이용자 행동 로그 | 어떤 인증 계정이 어떤 대상에 어떤 작업을 수행했는가 | 별도 JSONL 파일 |
| 관리자 운영 기록 | 누가 제재·설정·공지 등의 운영 조치를 했는가 | 기존 앱의 감사 모델 유지 |

개인정보처리시스템 접근기록은 관리자 개인정보 조회 등 별도 의무 검토 대상이다. 위 네 분류 중 어느 하나가 있다고 자동 충족되는 것은 아니다. 특히 이용자 본인의 행동 로그와 관리자의 개인정보 조회를 혼동하지 않는다.

참조 프로젝트의 최신 운영 문서에는 ‘관리자 조회 이력 제외’가 기록되어 있다. 이는 다른 프로젝트의 면제 근거로 복제하지 않는다. 대상 프로젝트의 명시적 요구·적용 의무를 확인하고 적용표에 포함 여부와 미충족 위험을 남긴다. 이 표준도 사용자 지시 없이 기존 프로젝트에 조회 이력을 소급 추가하는 권한은 아니다.

## 7. 이용자 행동 로그 공통 계약

### 7.1 원본 저장과 환경

```text
운영: C:\caddy\logs\AuditLog\<project_slug>\
개발: <project_root>\.runtime\user-actions\
일별: user-actions-YYYY-MM-DD.jsonl
```

project_slug는 소문자 영문·숫자·하이픈의 프로젝트 고유 이름이다. 프로젝트마다 디렉터리를 분리하고 다른 프로젝트 로그를 읽지 않는다. 운영 기본 루트는 현재 참조 프로젝트의 실제 운영 문서에 맞추었다. 이전 제안의 `C:\web\...` 예시를 새 프로젝트 기본값으로 섞지 않는다.

환경은 명시적으로 development/production으로 구분한다. 미지정 시 개발로 동작하되 운영 배포 점검에서 production 명시를 확인한다. 환경변수의 프로젝트 접두사는 달라도 다음 의미는 고정한다.

`환경 / USER_ACTION_LOG_ENABLED / USER_ACTION_LOG_DIR / USER_ACTION_LOG_RETENTION_MONTHS / 조회 기간 상한 / 페이지 크기`

프로젝트 DB에 행동 로그 원본을 넣거나 별도 클라우드 플랫폼으로 보내는 것은 표준 편차다. 자동으로 도입하지 않는다. 파일 저장과 DB 변경은 원자적으로 결합되지 않는다는 한계를 문서화한다.

### 7.2 스키마 v1

| 필드 | 공통 의미 |
|---|---|
| schema_version | 1 |
| event_id | 개별 이벤트 UUID |
| timestamp | UTC ISO 8601, 표시 시 KST |
| request_id | 서버 생성 요청 UUID. 한 요청의 여러 이벤트에서 공유 |
| user_id | 인증된 내부 회원 ID 또는 null |
| action | 고정된 domain.action 코드 |
| object_type / object_id | 실제 처리 대상과 ID 또는 null |
| outcome | success / failure / denied / noop |
| reason_code | 고정 사유 코드 또는 빈 값 |
| client_ip / ip_source | 신뢰 경로에서 확인한 IP·출처, 미확인이면 null/unknown |
| cf_ray | Cloudflare 보조 연결값 또는 null |
| route | 프레임워크 경로 이름. 원시 URL·쿼리 제외 |
| metadata | 허용 목록의 작은 상태 정보만 |

문자열 길이·IP·UUID·상태 형식을 검증한다. 새 필드는 버전·호환성을 기록한다. 다른 프로젝트에서 같은 이름으로 다른 의미를 저장하지 않는다. 정수 회원 ID가 아닌 프로젝트는 실제 불변 ID를 문자열로 보존하고 자료형 매핑을 명시한다.

### 7.3 행동 목록

공통 계정 코드: `account.signup`, `auth.login`, `auth.logout`, `account.delete`.

콘텐츠 코드: `<domain>.create/update/delete/visibility_change`. 예: `book_review.create`, `movie_review.update`, `quote.delete`. 반응은 `reaction.add/remove`, 신고는 `report.create`를 사용한다. 도메인이 달라지면 대상명만 추가한다.

지원하는 모든 사용자 변경 기능에 대해 `경로 → 실제 행동 → 대상 ID 확보 → 성공/실패/거부/변경 없음 → 테스트` 매핑표를 만든다. 경로 이름에 create가 있어도 기존 데이터 갱신이면 update다. 중복 신고 생성은 noop이며 반응 추가와 취소를 구분한다.

### 7.4 시점과 최소 수집

미들웨어는 요청 문맥만 준비한다. 업무 결과는 실제 뷰·서비스에서 기록한다. HTTP 200/302를 성공으로 간주하지 않는다. DB 변경은 커밋 이후 성공 이벤트를 기록하고 롤백 시 성공 로그를 남기지 않는다. 삭제·탈퇴·로그아웃 전 필요한 식별자를 값으로 확보한다.

로그인 실패에서 입력 아이디로 회원을 추정하지 않는다. 실패 결과와 IP·요청 ID만으로 처리하고 user_id는 null로 둔다. 성공 시 실제 인증된 회원을 연결한다.

비밀번호, 쿠키, 세션·CSRF·인증 토큰, POST 본문, 이메일, 입력 아이디 원문, 게시물·문의 원문, 검색어, User-Agent·Referer 원문은 행동 로그에 저장하지 않는다. 예외 문자열 전체도 metadata에 넣지 않는다. 진단에 필요한 상태값만 허용한다.

파일 쓰기 실패·디스크 부족을 숨기지 않고 별도 오류와 상태에 남긴다. 저장된 업무를 로그 실패 때문에 미처리라고 안내하지 않는다. 엄격한 무누락 요구가 있으면 파일 방식의 한계를 설명하고 별도 합의를 거친다.

## 8. 관리자 행동 로그 조회 UI 계약

메뉴 이름은 ‘이용자 행동 로그’, 기본 경로는 `/manage/user-actions/`다. 기존 ‘운영 기록’과 섞지 않는다.

| 순서 | 구성 |
|---|---|
| 1 | 제목 ‘이용자 행동 로그’와 조회 범위 설명 |
| 2 | 기록 상태: 활성 여부, 최근 성공/실패, 데이터 범위, 최근 파기·보존기간 |
| 3 | 기간 → 회원 ID → 행동 → 대상 종류 → 대상 ID → 결과 → 요청 ID → 조회·초기화 |
| 4 | 권한 있는 IP 검색 — POST 또는 서버 측 문맥, URL에 실제 IP 금지 |
| 5 | 시각(KST) / 회원 / 행동 / 대상 / 결과 / IP / 요청 ID |
| 6 | 조건을 유지하는 페이지 이동 |

기본 조회는 정확히 최근 24시간, 최대 한 번에 7일, 페이지 크기는 50으로 통일한다. 날짜만 받는 구현은 ‘어제~오늘’이 정확한 24시간이 아님을 명시하고 UI 문구·계산을 맞춘다. 과거 보관분도 7일 구간으로 조회할 수 있어야 한다.

필수 권한 이름은 `view_user_action_logs`와 `view_user_action_network`다. 프레임워크 앱 접두사만 매핑 가능하다. 기본 조회는 IP 마스킹, 실제 IP와 Cf-Ray는 네트워크 권한으로 제한한다. 마스킹은 HTML 표시뿐 아니라 응답 데이터에도 적용한다.

상세는 안전한 텍스트 렌더링, request_id 복사, 살아 있는 대상의 권한 확인 링크를 제공한다. 편집·수동 삭제·대량 내보내기는 기본 제외다. 응답은 no-store로 하고 커서 서명·만료·파일 변경·스캔량 제한을 처리한다. IP 검색 조건이 다음 페이지에서 사라지거나 URL에 노출되지 않게 한다.

폴더가 존재한다는 이유만으로 ‘정상’이라고 표시하지 않는다. 수집 실패, 데이터 없음, 미수집 기간, 조회 상한, 손상된 줄, 만료된 커서를 각각 구분한다. 실제 데이터가 없는 기간을 ‘해당 사용자의 행동 없음’으로 단정하지 않는다.

실제 IP·개인정보 열람에 대한 별도 접근기록이 필요한지 확인하고 해당 권한·기록·보관을 결정한다. 구현하지 않았다면 이 의무를 충족했다고 보고하지 않는다.

## 9. 보관·파기의 일관성

이용자 행동 로그의 운영 기준 후보는 달력 기준 3개월이며 프로젝트별 법적 근거와 목적을 확인한 뒤 활성화한다. 90일로 임의 치환하거나 6개월·1년으로 임의 연장하지 않는다. 법적 근거 없는 보존을 ‘보수적이므로 안전’하다고 설명하지 않는다.

참조 구현은 기록 발생 시 하루 한 번 일별 파일 정리와 수동 파기 명령을 제공한다. 트래픽이 없으면 파기가 지연될 수 있다. 이를 ‘매일 독립 실행’ 또는 ‘기간 만료 즉시 삭제’라고 다른 프로젝트에 설명하지 않는다.

공통 도입 시 `파기 트리거 / 시간대 / 월말·윤년 계산 / 경계일 파일 처리 / 최대 지연 / 무트래픽 처리 / 백업 / 실행 실패 확인`을 반드시 결정한다. 요청 시 정리만으로 필요한 파기 시점을 충족하지 못하면 주기 실행 등 보완을 운영 작업으로 제안한다. 별도 권한 없이 예약 작업을 만들지 않는다.

접속 로그, 행동 로그, 운영 기록, 개인정보 접근기록을 같은 기간으로 묶지 않는다. 기록 종류별 근거·기간표가 최종 기준이다. 과거 문서에 적힌 1년을 모든 로그로 확장하지 않는다.

미리보기 가능한 파기 명령과 실행 결과를 제공한다. 보존 예외는 대상·근거·종료 기준을 기록해 분리한다. 백업·복사본도 기간을 관리한다. 프로젝트 경로 밖이나 다른 프로젝트 파일을 삭제할 수 없게 한다.

## 10. 공통 서버와 앱의 책임 경계

서버 작업은 앱 코드 작업과 별도 문서로 보고한다.

- 실제 Caddy 설정을 확인한다. 저장소 예시를 운영 설정에 덮어쓰지 않는다.
- Cloudflare 경유·원본 우회 차단 또는 검증을 확인한 뒤 연결 IP를 신뢰한다. client_ip라는 이름만으로 실제 IP라고 판단하지 않는다.
- Django 생성 X-Request-ID를 Caddy 응답 로그에 기록한다. 사용자 입력 요청 ID를 주 식별자로 쓰지 않는다.
- CF-Ray는 보조값이며 유일성·실제 사람 식별을 보증하지 않는다.
- 회원 ID를 Caddy에 넣기 위해 응답 헤더로 공개하지 않는다.
- Cookie·Set-Cookie·인증 헤더 마스킹을 유지하고 검색어·쿼리·불필요 헤더를 최소화한다.
- 저장 경로·권한·회전·보존·백업·시각 동기화를 프로젝트 간 같은 방식으로 설정한다. 경로의 project_slug만 바꾼다.
- Caddy에 없는 요청 ID와 Cloudflare에서 차단되어 앱에 오지 않은 요청을 임의 재구성하지 않는다.

## 11. 수사기관 협조 운영 절차

목표는 ‘현재 보유한 자료로 계정·행동·요청의 연결 사실을 설명할 수 있음’이다. ‘경찰 수사에 90점’, ‘신원 확인 충분’, ‘source port만 더 있으면 완전’ 같은 근거 없는 평가를 사용하지 않는다.

1. 요청 기관·담당자·문서 진위를 확인한다.
2. 요청 자료 종류와 법적 근거·절차·기간·대상을 확인한다. 통신사실확인자료, 가입자 정보, 게시물 내용의 절차를 혼동하지 않는다.
3. 필요한 범위의 기존 기록만 검색한다. 존재하지 않는 user_id나 과거 행동을 URL에서 추정해 공식 기록으로 만들지 않는다.
4. 별도 보존이 정당한 경우 대상과 사유를 기록하고 원본을 임의 편집하지 않는다. 복사본·해시·추출 조건·담당자·시각을 남긴다.
5. 허용 범위만 제공하고 제공 이력·종료 후 파기 기준을 관리한다. 자동 전송 API는 기본 제공하지 않는다.

IP·계정은 실제 사람과 동일하지 않다. 삭제된 원문은 최소 행동 로그로 복원할 수 없다. 로그 파일과 DB의 연결에는 한계가 있음을 그대로 설명한다. 법정 보존 대상 여부는 프로젝트의 서비스·사업 형태에 따라 확인하며 신고 면제라는 이유만으로 의무가 없다고 단정하지 않는다.

## 12. 참조 구현의 취급

이 표준은 treview 논의와 구현을 참조하지만 treview 코드 전체를 검증된 공통 라이브러리로 인증하지 않는다. 특히 아래 항목은 그대로 복제하기 전에 검증한다.

- 요청 발생에 의존하는 파기와 무트래픽 보존 지연
- 관리자 개인정보 조회 이력의 포함 여부
- 화면의 ‘최근 24시간’과 날짜 기반 실제 범위 차이
- 저장소 존재와 실제 기록 정상 상태의 차이
- IP 검색과 페이지 이동의 조건 보존
- 로그 보관일과 상세 조회의 고정 검색일수 불일치 가능성

제안서보다 최신 운영 문서·코드가 사실 확인의 우선 근거지만, 코드에 있다고 요구사항이 충족된 것은 아니다. 참조 구현과 표준이 다르면 적용표의 차이로 보고하고 개선 또는 명시적 편차를 선택한다. 오류를 일관되게 복제하는 것을 표준화로 보지 않는다.

## 14. 버전과 편차 관리

각 프로젝트는 본 표준의 복사본과 `PROJECT-ADOPTION.md`를 보관한다. 공통 개선이 생기면 표준 버전·변경 요약·영향 프로젝트를 기록하고 기존 프로젝트에 일괄 적용하지 않는다. 각 프로젝트에 동일한 편차가 반복되면 표준 자체를 개정한다.

법적·기능적 차이는 정당한 편차다. 이유 없는 목차 삭제, 저장 방식 변경, 기간 변경, action 명칭 변경, IP 공개 범위 변경, 누락된 관리자 화면은 정당한 편차가 아니다.
